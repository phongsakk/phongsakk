ใช้กระบวนการ **2 บทบาท** แล้วสรุปเป็นเวอร์ชันตกลงร่วมกันก่อนลงโค้ด

แหล่งข้อมูลหลักหลังตกลง content แล้ว:

| ไฟล์ | บทบาท |
|------|--------|
| [`src/data/resume.ts`](../../src/data/resume.ts) | แหล่งความจริงบนเว็บ (TH + EN) |
| [`profile.md`](profile.md) | สรุปเนื้อหาแบบอ่านง่าย / อ้างอิง |
| [`review.md`](review.md) | ผลวิจารณ์จาก Recruiter (เขียนทับทุกครั้งที่มีรีวิว) |
| [`src/components/resume-view.tsx`](../../src/components/resume-view.tsx) | โครงสร้างการแสดงผล (ถ้าเปลี่ยนโครง section) |

เอกสาร agent อยู่ที่โฟลเดอร์นี้: `.cursor/docs/`

## 1. ภาพรวมกระบวนการ (2 ขั้นตอน)

```text
ข้อมูลดิบ (เว็บเดิม / GitHub / ประสบการณ์จริง)
        │
        ▼
[บทบาทที่ 1] ผู้สมัคร — ร่าง content เป็นวลี (ละประธาน)
        │
        ▼
[บทบาทที่ 2] Recruiter — วิจารณ์ → บันทึกที่ review.md เสมอ
        │
        ▼
เวอร์ชันตกลงร่วมกัน → อัปเดต resume.ts + profile.md → ตรวจบน /th และ /en
```

อย่าข้ามขั้นไปใส่โค้ดทันทีหลังร่างรอบเดียว — ต้องผ่านมุม recruiter และมี `review.md` ก่อน

## 2. สไตล์การเขียน (บังคับ)

เขียนเป็น **วลีสั้น / ประโยคที่ละประธาน** ไม่ใส่ “ผม” / “I” / “ฉัน”

| แบบที่ต้องการ | แบบที่ไม่ต้องการ |
|---------------|-------------------|
| ออกแบบ API และ pipeline ข้อมูลสำหรับระบบที่ทีมใช้จริงทุกวัน | ผมออกแบบ API... |
| โฟกัสตำแหน่ง Backend เป็นอันดับแรก | I'm looking for Backend roles... |
| แยกขั้นนำเข้า คัดกรอง และคำนวณก่อนบันทึกลง MySQL | ผมจึงแยกขั้นประมวลผล... |

### กฎเพิ่มเติม
- เน้น **โจทย์ที่เจอ → วิธีที่ทำ → ผลที่ได้** ไม่ใช่รายการหน้าที่อย่างเดียว
- ผลงานภายในองค์กร: **ห้ามใส่ลิงก์ / source code** อธิบายเชิงเทคนิคแทน
- ห้ามคัดลอกข้อความจาก GitHub README ทั้งดุ้น — เรียบเรียงใหม่ด้วยโทนวลีเดียวทั้งหน้า
- โฟกัสตำแหน่งตามลำดับ: **Backend → Full Stack → System Analyst**
- TH และ EN ความหมายสอดคล้องกัน (ไม่ต้องแปลคำต่อคำ)

### ตัวอย่าง Case Study

```markdown
### High-Performance Data Pipeline
- โจทย์ที่เจอ: ดึงข้อมูลภายนอกเฉลี่ยราววันละ 1 ล้านรายการ ต้องคำนวณทันใช้งานจริง
- วิธีจัดการ: แยกขั้นนำเข้า คัดกรอง และคำนวณด้วย PHP / Node.js แล้วเก็บเฉพาะผลที่จำเป็นลง MySQL
- ผลที่ได้: รองรับปริมาณระดับล้านรายการต่อวันได้ต่อเนื่อง
- Tech Stack: PHP, Laravel, Node.js, MySQL
```

## 3. บทบาทที่ 1 — ผู้สมัครงาน (เขียนร่าง)

### เป้าหมาย
ร่าง content ด้วยวลีละประธาน ให้เล่าโจทย์จริง อ่านแล้วเห็นผลกระทบ ไม่แข็งแบบเทมเพลต

### สิ่งที่ควรย้ายตำแหน่ง
| หัวข้อ | วางไว้ที่ | ไม่ควรวางที่ |
|--------|-----------|--------------|
| เรียนควบคู่ทำงาน full-time | ประวัติการศึกษา | สรุปคุณสมบัติ |
| เงินเดือน / ที่อยู่เต็ม / อ้างอิง | ไม่แสดงบนเว็บสาธารณะ | — |

### แหล่งข้อมูลที่ควรเช็กเพิ่ม
- เว็บปัจจุบัน: `/th` และ `/en`
- GitHub profile: https://github.com/phongsakk
- GitHub README: https://github.com/phongsakk/phongsakk
- นำมาเฉพาะสิ่งที่เกี่ยวกับตำแหน่งที่สมัคร

### โครง section ที่ต้องเขียน
1. สรุปคุณสมบัติ
2. ประสบการณ์การทำงาน (แต่ละตำแหน่ง)
3. สถาปัตยกรรมระบบภายใน (โจทย์ / วิธีจัดการ / ผล / Tech Stack)
4. ทักษะความสามารถ
5. ประวัติการศึกษา
6. ติดต่อ (รวม LinkedIn ถ้ามี)

## 4. บทบาทที่ 2 — Recruiter สาย Tech (วิจารณ์ร่าง)

### เป้าหมาย
ลดความรู้สึก “resume ทั่วไป”, ตรวจหลักฐาน, กัน skills กว้างเกินจริง

### บังคับ: บันทึกผลวิจารณ์ลง `review.md` เสมอ
ทุกครั้งที่ Recruiter วิจารณ์ร่าง **ต้องเขียน/เขียนทับ** ไฟล์:

`.cursor/docs/review.md`

ห้ามรีวิวแค่ในแชทแล้วจบ — ต้องมีไฟล์ `review.md` เป็นหลักฐานรอบล่าสุด

### โครงขั้นต่ำของ `review.md`

```markdown
# Resume Review

- วันที่:
- ร่างที่รีวิว: (เช่น หลังอัปเดตจาก GitHub / รอบแก้โทนวลี)
- ผู้รีวิว: Recruiter (สาย Tech)

## คะแนนแต่ละ section (1–10)

| Section | คะแนน | เหตุผลสั้นๆ |
|---------|-------|-------------|
| Summary | | |
| Experience | | |
| Case studies | | |
| Skills | | |
| Education | | |
| Contact | | |

## จุดที่เหมือน resume ทั่วไป
-

## จุดที่ขาดหลักฐาน / น่าสงสัย
-

## Skills ที่ควอร์เก็บ / ย้าย / ตัด
-

## ATS keywords ที่ขาดหรือควรเน้น
-

## ตัวเลขที่ควรถามเพิ่ม
-

## สรุปสิ่งที่ต้องแก้ก่อนขึ้นเว็บ
-
```

### Checklist การวิจารณ์
- [ ] จุดไหนฟังดู generic / คัดลอกเทมเพลต?
- [ ] จุดไหนขาดหลักฐาน (evidence) หรือตัวเลข?
- [ ] จุดไหนทำให้ recruiter ตั้งคำถามในใจ?
- [ ] Skills จาก GitHub สอดคล้อง Backend > FS > SA หรือดูเหมือน “รู้ทุกอย่าง”?
- [ ] Keyword สำคัญของ ATS สาย Backend/Full Stack ครบไหม?
- [ ] มี LinkedIn / ช่องทางติดต่อครบไหม?
- [ ] เขียนเป็นวลีละประธานครบทั้งร่างหรือยังมีประธานหลุด?

### เกณฑ์ตัด Skills
**เก็บใน skills หลัก:** สิ่งที่ใช้บ่อยในงานจริงและรองรับตำแหน่งเป้าหมาย  
**ย้ายไป “ใช้งานเป็นครั้งคราว / กำลังขยาย”:** สิ่งทดลองหรือใช้ไม่ถี่  
**ตัดออกจากหน้าเว็บ (เล่าตอนสัมภาษณ์แทน):** สิ่งที่รู้คร่าวๆ / ไม่ได้ลงลึก / ทำให้ดูกว้างเกิน

## 5. เวอร์ชันตกลงร่วมกัน (ก่อนลงเว็บ)

1. โทนวลีละประธานทั้งหน้า (TH/EN)
2. มี `review.md` ของรอบล่าสุดครบ
3. ผ่านการตัดทอน skills ให้โฟกัส Backend
4. Case study มี โจทย์ / วิธีจัดการ / ผล
5. เรื่องเรียนควบคู่อยู่ที่การศึกษาเท่านั้น
6. อัปเดต `src/data/resume.ts` เป็นแหล่งความจริงบนเว็บ
7. อัปเดต `profile.md` ให้ตรงกับเวอร์ชันตกลง

## 8. สิ่งที่ไม่ควรทำ

- ใส่ประธาน “ผม” / “I” ในเนื้อหา resume บนเว็บ
- ใส่ลิงก์โปรเจกต์ภายในองค์กร
- อ้างตัวเลขที่ไม่มีหลักฐาน
- ยัด tech ทุกอย่างจาก README ลง skills หลัก
- รีวิวในแชทอย่างเดียวโดยไม่เขียน `review.md`
- ให้ TH กับ EN คนละความหมายจนดูเป็นคนละโปรไฟล์
